# Iterasi #4 — animasi dial gelombang berhenti saat dial tidak terlihat

## Akar masalah (dari trace QML, bukan tebakan)

`perf record` masih terblokir (`perf_event_paranoid=2`), jadi atribusi diambil
dari **QML profiler lewat TCP** (`qs --debug <port>` + `qmlprofiler -a`), yang
tidak butuh ptrace. Trace 19 detik pada idle menunjukkan, per detik:

| Event | Frekuensi |
|---|---|
| `MaterialDial.qml:116` binding `path` | ~167/dtk |
| `MaterialDial.qml:159` `waveOffset` | ~330/dtk |
| `point.js constructor` (dipanggil path) | 3.000–5.000/dtk |
| `cubic.js anchor0X/anchor0Y` | ~1.100/dtk masing-masing |
| `polygon-measure.js measureCubic` | ~250/dtk |

`MaterialDial` hanya dipakai oleh `PlayerContent` (kartu media). Di sana dial
memang **tidak pernah terlihat kecuali kursor meng-hover artwork**:

```qml
opacity: artHover.hovered && root.t < 0.5 ? 1.0 : 0.0
```

Tapi animasi gelombangnya `running: true` tanpa syarat, jadi setiap frame
membangun ulang path bezier dial yang transparan. Itu biaya JS terbesar di
idle — lebih besar dari lirik, spinner, atau timer service.

## Perubahan

`modules/common/widgets/MaterialDial.qml` (1 baris + komentar):

```qml
running: control.visible && control.opacity > 0   // sebelumnya: true
```

Tidak ada perubahan yang terlihat: dial tetap beranimasi saat opacity-nya > 0
(host memunculkannya saat hover), dan berhenti saat transparan.

## Angka (satu sesi, `measure.sh`, 10 detik per sampel)

Kondisi: musik **Paused**, 1 monitor `eDP-1` 1920×1080@144, panel tertutup,
45 detik settle setelah restart, sampel diambil berurutan.

| Kondisi | n | min | median | max |
|---|---|---|---|---|
| tanpa gate (HEAD `93bd921`) | 8 | 8,24 % | **11,98 %** | 15,05 % |
| dengan gate dial | 10 | 2,11 % | **2,20 %** | 3,75 % |
| gate dial, verifikasi akhir | 6 | 2,01 % | **2,07 %** | 7,02 % |

Median turun **11,98 % → 2,20 %** (≈ 82 %), dengan sebaran yang jauh lebih
sempit. Satu sampel 7,02 % pada verifikasi akhir adalah burst periodik yang
juga muncul di semua kondisi (page fault ~2.000/dtk selama ±20 detik); bukan
regresi gate.

Kontrol tambahan: dengan seluruh isi sidebar kanan tidak dibangun
(`sidebarContentLoader.active: false`, 2×20 detik) idle terukur 1,79 % dan
4,80 % — praktis sama dengan gate dial. Artinya gate ini mengambil hampir
seluruh biaya yang dulu dibayar isi sidebar kanan, tanpa mengubah kapan isinya
dibangun.

RSS tidak berubah (≈ 1,08 GB) — ini perbaikan CPU, bukan memori.

## Gate

1. **Sintaks**: `/usr/lib/qt6/bin/qmllint modules/common/widgets/MaterialDial.qml` — tanpa error.
2. **Log**: tidak ada error/warning baru. Yang tersisa hanya
   `BarContent.qml: Cannot assign to read-only property "mirrored"` yang sudah
   ada sebelum perubahan ini.
3. **Visual**: `shot.sh --sane` S1 (bar) stddev 0,262 PASS; S2 dengan sidebar
   kanan terbuka stddev 0,186 PASS. Screenshot `shots/S2-fix4-dial.png`
   menunjukkan kartu media ("Lucky Bon Bon") dan artwork tetap tergambar.
4. **Manual (user)**: buka sidebar kanan, hover artwork kartu media — dial
   volume bergelombang harus beranimasi; pindahkan kursor — gelombang berhenti
   dan dial memudar. Ini satu-satunya perilaku yang disentuh.

## Yang tidak diubah

- **Spinner `MaterialLoadingIndicator` dan `StyledSlider`** sempat diberi gate
  visibilitas jendela juga. Hasil ukur tidak berbeda dari gate dial saja
  (median 2,08 % vs 2,20 %, dalam derau), jadi kedua perubahan itu
  **dikembalikan** agar diff tetap satu penyebab. Trace menunjukkan
  instance-nya memang ada di jendela yang terlihat (spinner/slider itu sah
  beranimasi).
- **Isi sidebar kanan tetap dibangun saat startup.** Membangunnya saat pertama
  dibuka memang menurunkan CPU ke angka yang sama, tetapi mengubah
  kehangatan buka pertama (Player + artwork + blur dibangun di depan user).
  Tidak diperlukan setelah biaya dial hilang.

## Kandidat ikon KDE Connect 0-byte — ditolak

`Error decoding: file:///tmp/kdeconnect_syoxide/…: Unsupported image format`
muncul 53 kali di log (31 path unik, semuanya file 0 byte) saat halaman phone
dibangun. Diukur 65 detik kemudian: **delta 0** — tidak berulang, tidak ada
biaya decode berkelanjutan. Perbaikannya (flag `Image.Error` per instance)
hanya akan menghapus 53 baris log sekali per sesi, tanpa angka resource yang
bergerak. Tidak dikerjakan.
